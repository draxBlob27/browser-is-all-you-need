# Aider Expansion-v1 Remediation Team

Parallel audit -> fix -> re-audit loop over the generated task families under
`.w8-biayn/data/aider-tasks-expansion-v1/`, producing a high-quality task set
for future SFT aimed at Aider Polyglot C++ improvement. This skill is the
team protocol; the per-family audit/fix method is
`.agents/skills/aider-task-family-remediation/SKILL.md` plus
`docs/aider-tasks-spec/verify-and-remedy.md`, which every worker MUST follow.

## Scope and exclusions

- In scope: every `<topic>/<family>/` directory under
  `.w8-biayn/data/aider-tasks-expansion-v1/` whose tasks are generated by an
  owning generator under `src/w8_biayn/integrations/`.
- Permanently out of scope: `aider-fixed26-analogs/` (actively worked on by
  another team). Never read, claim, audit, or modify it.
- Never edit existing skills, `AGENTS.md`, or another family's tree while
  working a claim. New team artifacts only: this skill, the lock directory,
  and per-family reports.
- This campaign creates no JSONL rows, splits, exports, token/mask evidence,
  or dataset-release claims.

## Team roles

- **Orchestrator** (one): inventories families, seeds the lock directory,
  launches workers in waves, resumes timed-out workers, re-audits worker
  claims, and writes the final campaign report.
- **Worker** (one per family): claims exactly one family, runs the loop below,
  and reports. A worker touches only its claimed family tree, that family's
  owning generator + focused test, and its own lock/report files.

## Lock protocol (`.remediation-locks/`)

Lock directory: `.w8-biayn/data/aider-tasks-expansion-v1/.remediation-locks/`.
One file per family: `<topic>--<family>.json`.

1. Claim atomically before any work:
   `set -o noclobber; > lockfile` or `mkdir`-style creation. If the file
   exists, the family is claimed — skip it, do not inspect or modify it.
2. Claim file content: `family_path`, `owner_generator`, `worker_id`,
   `claimed_at` (UTC ISO), `status`
   (`in_progress | done | blocked | abandoned`), `heartbeat_at`,
   `last_tree_hash`, `notes`.
3. Update `heartbeat_at` and `status` as work progresses. On finish set
   `status: done|blocked` with the final tree hash; never delete claim files —
   they are the campaign ledger.
4. Stale-claim recovery (orchestrator only): a claim whose `heartbeat_at` is
   older than 60 minutes with `status: in_progress` may be re-claimed after
   checking no live process references the family. Record the takeover in the
   claim's `notes`.
5. Before regenerating, re-check that no `.cycle-*` or receipt file changed
   since the audit began (hash drift not caused by the worker = another agent
   is active; abandon and re-claim later).

## Worker loop (per family)

Follow `aider-task-family-remediation` end to end. In brief:

1. **Read**: `AGENTS.md`, this skill, `aider-task-family-remediation`,
   `docs/aider-tasks-spec/verify-and-remedy.md`,
   `docs/aider-tasks-spec/prompts/implement-family-for-sft.md`, the family's
   curriculum/spec doc, the owning generator, and its focused test.
2. **Audit** the current tree: hash/receipt binding, structural/role contract,
   prompt boundary (docs vs hidden-test rules), primary core objective per
   root (sampled + mechanical sweep over all roots), hard-diversity/family
   screen evidence, adversarial controls, contamination screens, ledger
   hygiene. Record findings with severity per verify-and-remedy.md.
3. **Fix root causes in the owning generator** (never hand-edit generated
   output), updating the curriculum/spec and focused test in the same change.
4. **Regenerate** the family through its owner only.
5. **Host verify** (this campaign's done gate; see below).
6. **Re-audit** the regenerated tree: every prior finding must be closed with
   named evidence; re-run the hard-rule screen and adversarial controls
   through the owner; confirm receipts bind the new tree hash.
7. If the re-audit finds new issues, loop to step 3. A worker is done only
   when an audit pass produces zero blocker/major/moderate findings.
8. Write the report (below), then set the claim to `done` (or `blocked` with
   the exact blocker).

## Done gate (this campaign: host verify)

The user set this campaign's verification strength to **host verify only**:

- Run the owning generator's host verification (e.g. `--verify-host` or the
  owner-designated normal + fresh ASan/UBSan reference build/run on the host,
  including negative-fixture rejection) for every root, plus the owner's
  structural/family-screen verification (`--verify-core` or equivalent).
- Host toolchain: use the project venv (`uv run ...`) which provides
  `cmake 4.4.0` and `c++ (GCC 13.3.0)`. Do not install anything system-wide.
- Docker sanity is **not** part of this campaign's gate. Do not run Docker.
  Record existing Docker receipts as-is; record fresh Docker evidence as
  `not_completed (campaign gate: host verify only)`.
- Therefore no family in this campaign may be newly claimed
  `local_family_verified` — that status still requires the mandatory
  network-disabled Docker sanity run per `aider-task-family-remediation`.
  The strongest claim a worker may make is:
  `campaign_verified_host_only` (audit pass + owner host verify pass +
  hard-rule screen pass + receipts bound to current tree).
- If an owner lacks a host-verify mode, use its strongest existing verify
  entry point; if none exists, record `not_completed` with the exact missing
  command and set the claim `blocked`.

## Worker report

Write `<family-root>/.state/remediation-team-report.json`:

```json
{
  "schema_version": "expansion-remediation-team-report-v1",
  "family_path": "<topic>/<family>",
  "owner_generator": "<repo-relative path>",
  "worker_id": "<id>",
  "cycles": [{"audit_findings": ["..."], "fixes": ["..."],
              "tree_hash_before": "...", "tree_hash_after": "..."}],
  "final": {
    "tree_hash": "...", "root_count": 0,
    "host_verify": "pass|fail|not_completed",
    "family_screen": "pass|fail|not_completed",
    "docker_sanity": "not_completed (campaign gate: host verify only)",
    "open_findings": [],
    "strongest_status": "campaign_verified_host_only|blocked|not_completed"
  }
}
```

Keep hidden-test and reference contents out of the report (behavior summaries
only). The orchestrator re-reads these reports and spot re-audits before
accepting a worker's `done`.

## Phase 2: docs alignment

When the campaign enters the docs-alignment phase, workers audit and fix each
root's `.docs` (instructions.md + introduction.md) against the official
benchmark conventions using
`references/docs-alignment-rubric.md`. All other rules of this skill still
apply; claims for this phase live in `.remediation-locks/docs-phase/`.

## Guardrails

- Never hand-edit generated task output; change the generator/scaffold/config
  and regenerate.
- Never weaken a spec, test, or screen to make an audit pass; report policy
  contradictions instead.
- Reject (replace) roots with benchmark overlap or unfixable triviality; keep
  the permanent-holdout boundary (all 26 official Aider Polyglot C++ roots).
- Respect count bounds in each family's curriculum; satisfy them only with
  roots passing the seven-dimension hard diversity rule.
- After any generator/artifact change, invalidate and refresh that family's
  receipts through the owner-controlled path before claiming done.
- One family per worker at a time; no cross-family edits; no git mutations
  (no commits, no resets).
